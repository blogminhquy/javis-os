# E1 technical-outcome issuance resolution

Design resolution, 2026-10-24. Resolves question 1 in `effective-skill-builder-check.md`. Read-only source basis: committed `411e8c49` and the Q1/Q2 design at `ba258557`; public effective-skill spec/root preface read as requested. No Q1 working files, app imports, tests, SDK/native execution, probes, or Git mutations were used. Only this report is written. All new names below are proposed contracts, not implemented facilities.

## Decision

E1 owns a small, synchronous data-evaluation transition inside the **existing QualificationSession owner**, followed by its existing proposed ActivationOwner technical admission. It evaluates the actual authenticated baseline and candidate skill bytes against one fixed host engineering profile. It issues a private `TechnicalManualDecision` only after a complete, reproducible technical win with preserved regression constraints. M2F later calls this producer; M2F is not its issuer or prerequisite.

The first profile is deliberately `skill-byte-transition-v1`: it proves a disposable byte-selection/transaction workflow, not that a model used or improved a skill. It must be recorded and displayed under that exact coverage. No production acceptance, native execution, independent dataset, semantic review, pilot, or business eligibility is inferred. This replaces the original report's undefined prerequisite "simulation workflow records" with the precise records and transitions below. It does not weaken the product path.

Do not make `ComparisonResults`, `TrialResults`, `OperationResults`, or `SemanticReview` publish synthetic successful product evidence. Do not make Q2 invent an artifact/evaluation field. There is no extra executor, workflow scheduler, business-acceptance issuer, schema table, CallLedger entry, or native/model invocation for this transition.

## Why this is the smallest compatible construction

At `411e8c49`:

- `improvement_comparison_results.py:96` `aggregate` is pure arithmetic over already authenticated evidence. `project_result` at line 180 requires a product report, and `ComparisonResults` categorically calls `require_product_store`. Its numeric/selection verdict always retains business eligibility and independence as unverified. A technical event cannot be disguised as that report.
- `improvement_cases.py:61` `_contract` requires both mandatory and business criteria, with a business primary metric. `improvement_evaluation.py:198` `evaluate_trial` uses that contract and a host checker registry. Reusing that whole contract for a byte marker would introduce misleading business fields. Do not relax it or manufacture an owner-confirm/business checker.
- `team_acceptance.py:203` `check_one` already evaluates `file_contains` as data and returns pass/fail/unknown with the hash/size of the actual bytes. This narrow structural primitive can be reused without an AcceptanceStore, command runner, Team task, or product evaluation record. Its contains check is case-insensitive; the technical profile preserves that behavior explicitly.
- `SkillCandidates` at `improvement_skill_candidates.py:31` already owns current target/context/grant checks, descriptor-safe canonical observation, authenticated candidate provenance/patch reconstruction (`read_proposal`, line 103), editable-region declaration (212), staging (264), and exact-diff authorization (355). These supply actual authoring authority and bytes, not outcome quality.
- `QualificationSession` at `improvement_qualification_session.py:73`, `open` at 79 and `_assert_native_current` at 288 supplies the actual disposable root/store/principal/run/source lifetime. It gains a technical evaluation entry, not a second kind of Session. Current Session is necessary but insufficient: the newly specified evidence transition must also succeed.

The frozen Q2 design at `ba258557` defines `QualificationQueryResult` with no activation verdict or product output/evaluation ID. Its publisher authenticates real attempt/link/trace/cleanup evidence. That type must remain exactly what its final implementation says. Its retained-owner discipline and cold/live distinction are reused below. Its native checks cannot be relabeled as passing model/business checks.

2. One actual user-owned, enabled canonical skill in that disposable brain; actual `ImprovementStore.capture` target/current revision and immutable baseline blob; disposable suggest policy only. Ordinary production policy is never changed.
3. One genuine `HostContextStore.create` context/grant for the owner DM, actual selected engine/config and the captured target. The authoring experiment/context identifier need not have a product comparison/report. If a full experiment row exists, preserve its normal editable/unsealed fences. 4. An actual `SkillCandidates.declare_region` authorizes the fixture body's editable region before plan freeze. E1 profile v1 requires this predeclared region; it does not use the stage-then-authorize-diff path, which cannot meet this plan's no-candidate freeze precondition. Preserve canonical frontmatter, implicit description, ownership/enable state, source permissions and dependency/reference inventory. E1 uses a no-dependency fixture to make dependency equality independently checkable; it does not publish a semantic-review pass.
5. Freeze the technical plan described below **before candidate staging**. There must be zero staged candidates for that authoring context/experiment at freeze. No product selection, proposal operation, comparison schedule or trial is required.

The real existing context/baseline/edit grant/candidate records plus the frozen plan and evaluation event **are** the minimal E1 technical workflow. They are enough to call the same materialize/ready/CAS/read/revert core. A native query, installed qualification proof, model output or M2F record is not a hidden prerequisite for the static-byte profile. This does not close D1, E3, full native D2, or M2F.

## Exact profile and plan

One host-owned profile constant, no user-provided rules/callables/commands/paths:

- profile id `skill-byte-transition`, version 1;
- coverage `authenticated_skill_bytes_only`;
- checker `team_acceptance.check_one`, restricted to `file_contains`, with `run_command=None`, `since=0`;
- one fixed relative scratch name `skill.txt` for each variant;
- improvement case `instruction_marker`: `must_contain=["E1 fixture: candidate instruction present."]`, `min_chars=1`;
- regression case `preserved_marker`: `must_contain=["E1 fixture: preserve this line."]`, `min_chars=1`;
- exactly two variants baseline/candidate and exactly one evaluation of each case per variant: four expected cells. No statistical independence or repeated-sample claim.

The caller creates fixture bytes through actual authoring paths; it cannot choose the rule or the result. The happy baseline body contains only the preserved marker plus ordinary fixture prose. The staged candidate preserves that marker and adds the instruction marker. Thus the win is a consequence of evaluated bytes, not an expected-outcome parameter. These literal markers belong only to the private engineering profile, never general product acceptance logic.

Proposed host-only Session entry points (implemented with the E1 owner, not exposed through HTTP/MCP/Dashboard):

```
freeze_skill_transition(authoring, *, context_id, target_id, selector,
                        expected_target_generation, expected_policy_version,
                        event_key) -> TechnicalSkillPlan

evaluate_skill_transition(authoring, plan, *, candidate_id,
                          event_key) -> TechnicalSkillOutcome

issue_skill_decision(activation_owner, outcome, *,
                    expected_activation_generation, decision_key)
    -> TechnicalManualDecision
```

`authoring` must be the concrete same-store SkillCandidates owner, with its pack-state/source ownership already checked. `activation_owner` must be the exact proposed `ActivationOwner.for_qualification(self)` instance. Principal/domain/root come from Session. Selector passes the public design's exact owner-DM/config/context resolution; a caller mapping never establishes its truth. No checker registry, outcome boolean, raw bytes, expected verdict, output path, callback, QueryResult mapping, or arbitrary event id is accepted.

Closed `TechnicalSkillPlanV1` serialized fields:

```
version=1, domain='qualification', supported=False, account_ready=False,
business_proof=False, coverage='authenticated_skill_bytes_only',
run_hash, plan_id, profile_id, profile_version, profile_hash, checker_source_hash,

base_revision_id, base_hash, target_generation,

edit_authority_id, edit_authority_generation, source_authority_hash,
frontmatter_hash, dependency_hash
```

`plan_id` is host-derived from canonical plan content excluding itself; event key is only replay identity, never authority. Persist canonical encrypted plan blob and an `effective_skill_technical_plan` event containing its id/hash/blob reference. Use existing `_event`/`_replay`; the plan freeze transaction rechecks actual context/grant/source/target and the no-candidate condition. Its current source pin includes the actual checker/profile implementation bytes. Unknown fields and bool-as-int reject. The exact plan object is registered by the Session after a successful append; caller construction, copying a dataclass or deserializing its JSON cannot produce a live plan.

The no-candidate precondition is specific to freezing this engineering plan, not a new global authoring restriction. Loss/tie/unknown controls use separate disposable contexts/runs. M2F can construct each explicitly without changing a verdict after the fact.

## Evaluation, outcome and actual issuance

`evaluate_skill_transition` owns this whole sequence, retained in the final Q1/Q2 Session host-operation mechanism before any off-loop work. Do not add another task lifetime registry if Q1 already supplies the concrete retained-owner interface. The publisher can ignore only its own exact publishing task when checking its completion; other work remains retained and blocks Session.cleanup as appropriate.

1. Require the Session-registered exact plan, authenticate its encrypted event/blob, and check source/profile pin and current Session. Load current candidate/context/target/edit authority using SkillCandidates. Authenticate `read_proposal` and its reconstructed bytes against both immutable base/candidate hashes and actual canonical observation. Require the one post-plan ordinal-1 candidate; content equality is permitted for tie diagnostics. Validate body-only change, unchanged raw prefix/frontmatter/description and dependencies. Missing/foreign/tampered/stale identity or revoked authority is an admission error, not a low-quality result.
2. Hold byte-exact baseline/candidate data copied from those authenticated sources. Create private scratch copies under Session.root, through the same descriptor/ancestry containment discipline as E1 materialization; never hand the checker a canonical path or caller path. Check each copy's hash/size before and after checking. Retain scratch/file futures through cancellation; clean them before successful publication.
3. Run `check_one` on all four fixed cells. Check its returned hash and size against the authenticated corresponding variant, and accept only the closed verdict pass/fail/unknown. Persist bounded deterministic evidence (case id, variant, source hash/size, verdict, reason code); omit scratch path/mtime and private exception text. The source checker evaluates copied data, never code. A checker/storage error or unreadable copy means unknown coverage; an altered copy/hash mismatch invalidates that evaluation. Neither may yield a pass. Never catch a Session/permission/source identity failure and reinterpret it as an admissible result.
4. Compute the outcome within the producer, from those actual cells. A complete cell means authenticated source identity, unchanged byte copy and a recognized non-unknown checker verdict. `complete=True` requires all four. For each case: fail→pass is win; pass→fail loss; equal recognized verdicts tie; anything unknown/incomplete unknown. Result `win` requires complete improvement win **and baseline+candidate regression both pass**. Result `loss` is complete improvement loss or any observed candidate regression fail; result `tie` is complete improvement tie with both regression passes; otherwise `unknown`. A regression fail never becomes a win because another cell passed. A candidate still failing both cases cannot be eligible through ties. Record per-case outcomes even when the overall result is loss/unknown.
5. Serialize encrypted `effective_skill_technical_outcome` evidence, then in the final writer transaction repeat Session/current source/profile/candidate/plan/event/grant/target/policy checks after slow blob writes. Recompute the summary from captured authenticated cells; append the event only if all captured identity joins still match. No mutable trial state, experiment phase, product selection/report or billing row is changed. Source/CAS conflict leaves no authoritative result; orphan encrypted bytes are not an outcome.
6. Register the exact immutable outcome object in the live Session **only after the durable append**. Its registration binds exact Session, plan object, authoring owner and event digest. Publication failure retains the original pending proof operation for retry without rerunning an ambiguous append. Idempotent replay reauthenticates the stored evidence and current authority before issuing a new live handle; a cold reader never does this. Closed/expired Session can retain diagnostics but cannot create new usable outcome/decision handles.

Closed `TechnicalSkillOutcomeV1` fields:

```
version=1, domain='qualification', supported=False, account_ready=False,
business_proof=False, business_eligibility='unverified', independence='unverified',
coverage='authenticated_skill_bytes_only',
run_hash, outcome_id, plan_id, plan_hash, candidate_id,
candidate_hash, candidate_provenance_hash, candidate_stage_event_hash,
authority_binding_hash, cells, complete, case_outcomes, outcome,
checker_source_hash, profile_hash, evaluation_evidence_hash, cleanup_evidence_hash
```

`cells` is exactly the four ordered `(case_id, variant)` records above, with `source_hash`, `byte_size`, `verdict`, `reason` and `integrity` (pass/fail/unknown). `case_outcomes` has exactly instruction_marker/preserved_marker. Hashes are canonical hashes except raw content hashes. `authority_binding_hash` hashes the authenticated current context/target/grant/policy/source facts in the evaluation evidence; it is a consistency join, not permission. `outcome_id` is host-derived from canonical content excluding itself. Cleanup evidence is owner-produced scratch cleanup, not Q2 native cleanup. These fields must not claim a native attempt, result, call, installation or delivery that did not occur.

`issue_skill_decision` is the only constructor for a live TechnicalManualDecision. It requires:

- exact registered live outcome and plan from this Session; authenticated unique plan/outcome event/blob; exact concrete same-session ActivationOwner;
- outcome `win`, complete four-cell coverage, all integrity pass, improvement fail→pass and both regression pass; no unknowns or regression loss;
- recomputed profile/source pins, authenticated immutable byte identities and fixed-rule verdicts agreeing with the evidence; no caller-supplied projection or cached verdict is trusted;
- current live Session and unchanged target, canonical source, context/grant, body edit authority, prefix/dependencies, selector/config/profile and policy; existing product/business gate is not called or changed;
- exact activation-generation CAS and immutable expected materialization manifest derived by the owner, plus a fresh or exact-replay decision key.

The private decision binds Session identity, ActivationOwner identity, run/plan/outcome hashes, candidate and manifest hash, exact selector, expected target/policy/activation generations and decision-key payload hash. It has a private constructor and Session registration; it is neither a public JSON type nor obtainable from `TechnicalSkillOutcome.read_stored`. The decision event is appended using existing events. The result's business fields remain unverified even when the decision exists.

Use this decision in `ActivationOwner.apply_simulation` instead of the undefined workflow/comparison_report prerequisite. Give the technical request its own exact internal fields (`outcome_id`/`outcome_hash` plus the expected generations/manifest/selector/decision key); never stuff a technical outcome id into public `comparison_report_id`. The product request/parser and acceptance_pending refusal remain unchanged. Both internal admissions enter the same prepare→ready→pointer-CAS core. Core validates live issuer/domain/identity on entry, after awaits and at commit. The accepted technical pointer/pin/event stores plan/outcome/decision refs and coverage, so an ordinary factory refuses it even if presentation labels are removed.

Once the pointer commits, its immutable decision/provenance is durable. The *live* technical use still requires the exact retained Session/turn owner and current source/permission checks. Cold history is readable; it cannot create a new live Session, reapply or reopen a turn. Revert keeps the original design's independently checked prior pin/current-generation authority; it does not need a newly fabricated win. Close, revoke, target drift or foreign-root mismatch denies new apply/use regardless of an old win.

## Unknowns, caller forgery, replay and recovery

A caller may choose valid fixture content and an authorized edit; it cannot assert the checker result. The fixed rules are frozen before candidate creation, and both actual byte versions are checked. That is sufficient authority for an explicitly bounded disposable engineering exercise, not independent business evidence.

An arbitrary `_event` insertion, copied live object, supplied `win=True`, fabricated query mapping, foreign Session, cold outcome id, stripped domain field, changed rule or replay key cannot construct a registered decision. At issue/apply the owner reauthenticates and rederives the byte checks and all durable joins. An unrecognized duplicate event fails closed. This protects the public/service boundary; it does not pretend to secure Python process internals from trusted code that can mutate private object registries or replace the application.

Loss, tie and unknown remain durable technical outcomes with no decision and no new materialization/pointer. Baseline is used in a fresh scope. Incomplete evidence is not success. A corrupted/tampered identity or source permission change is refused before decision; it is not converted into a legitimate comparison loss. A missing/failed native proof is still native unknown even if this independent static-byte profile won.

Crash after a plan/outcome append leaves readable history. Recovery never reconstructs live authority from SQL alone. Within the surviving exact Session, retry can authenticate and recompute a replay before producing a new registered handle. After Session closure/loss, new E1 work needs a new actual Session and genuine prerequisites; forensic reopening stays read-only. Pending materialization recovery and pointer CAS remain the E1 shared core from the public design. Publication/decision-key replay cannot select a newer candidate or refresh expired authorization.

## Q2 and M2F boundary

Final Q2 proof types/method signatures must be consumed as landed. E1 reuses their Session host-operation retention and exact live-versus-cold proof ownership discipline, not their domain-specific native completion receipt. A Q2 `QualificationQueryResult` alone is never the outcome above: completed protocol, trace integrity, input delivery and cleanup are not improvement quality; production native_qualification may remain unknown.

M2F may attach an independently cold-authenticated Q2 proof as separate provenance in its own integrated workflow event, joined by the exact run and actual request/materialization/input identity. Merely being in the same Session does not prove that a query consumed this skill/candidate. The E1 outcome schema deliberately has no optional arbitrary query field. If M2F wants a *query-output* quality profile later, it needs a separately versioned genuine output capture/evaluation contract; this design grants no such claim and E1 does not depend on it.

M2F's required win/loss/tie/unknown lifecycle can call this same static technical producer and then the real apply/read/revert path, while separately proving D1 query lifecycle and accounting through authentic Q2 records. The integrated report must name each coverage dimension. It cannot describe four marker checks as model improvement, genuine business acceptance, complete native D2, or installed qualification. Actual native effective-profile inability remains OPEN; normal native baseline remains existing behavior.

## Concrete E1 acceptance setup and controls

The implementer can construct the positive vertical without M2F:

1. Create the real disposable Session/store/brain; capture fixture canonical skill, create its real host context, declare the editable body region, and freeze the fixed profile plan.
2. Stage the real body patch adding the instruction marker while preserving the regression marker, raw frontmatter and dependency inventory.
3. Evaluate all four actual checks. Assert the immutable outcome joins authentic authoring bytes/events and yields the required complete win; issue the private decision through the Session producer.
4. Apply through the shared materialization/ready/CAS transaction. Open the actual simulated owner-DM API TaskSkillScope, exercise the real router/lazy/hub read, and verify candidate bytes/pin/usage receipt. Revert through the same activation owner, then a fresh turn reads baseline. Canonical skill bytes never change.
5. Assert product APIs and ordinary runtime factories still refuse all qualification records, product reports/result_json remain absent, and no query/call/budget debit was invented for the structural evaluation.

Separate real controls construct baseline containing both markers then remove the instruction marker (loss); leave a baseline without the instruction marker unchanged (tie); add instruction marker while removing regression marker (regression veto). For unknown, exercise a genuine checker/copy unavailability or recorded incomplete evaluation through an explicitly labeled fault fixture and require no decision. Do not insert a prebuilt unknown/win event as positive issuer coverage. Corrupt proof/event, wrong candidate/session/store, rule drift, grant revoke, source change during publication, repeated cancellation, append failure, stale activation generation and cold replay must refuse or retain incomplete evidence at their actual boundaries. These are focused E1 integration checks, not a second native qualification matrix.
